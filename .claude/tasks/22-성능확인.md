요청서는 "TO_CHAR/EXTRACT/YEAR 쿼리가 현재 형태", "(external_id, category) 유니크가 있는지 확인", "범위 조건 전환은 후속 task"라고 가정했다. 코드로 확인하니 이미 바뀌어 있었다.
- 모든 월/연 조회 쿼리가 이미 `[start, end)` 범위 + `member_id` 조건이다 (task 17, decisions 2026-10-28). → 측정의 "이전 형태(old)"는 **현재 코드가 아니라 SQL로 재현한 옛 모양**이다. "3단계(range)"가 현재 코드 모양이다. 따라서 "범위 전환을 후속 task로 제안"은 해당 없음.

- 스키마는 Flyway/마이그레이션 파일 없이 `ddl-auto: update`로 만들어진다(application.yml의 해당 줄만 확인, 접속 정보는 읽지 않음). → 선언한 제약/인덱스가 **실제 DB에 있는지는 코드만으로 알 수 없다** (아래 C-2, `22-perf/90-check-real-schema.sql`).

## A. 월별 조회 / 캘린더 쿼리 EXPLAIN 전후 비교

### 방법과 실행 환경 (중요)
- psql이 없고 Docker가 꺼져 있어, 요청서 방식(Supabase SQL Editor에서 사용자가 실행)을 위해 SQL을 만들었다. 그 뒤 **스크립트가 실제로 도는지 검증하려고** Docker Desktop을 켜서 **로컬 일회용 PostgreSQL 17 컨테이너**에서 같은 파일을 그대로 실행했고, 아래 표는 그 결과다. **Supabase에는 접속하지 않았다.** 컨테이너는 측정 후 삭제했다.
- 따라서 아래 숫자는 "내 PC의 Docker PG17" 값이다. 절대 시간은 Supabase와 다르다(네트워크·하드웨어·shared_buffers). **Scan 방식과 읽은 버퍼 수의 상대 비교**가 의미 있는 값이다. Supabase 결과는 사용자가 `00-setup.sql`~`30-...sql`을 실행해 붙여준 값이며 아래 "Supabase 결과"에 있다 (같은 10만 건 데이터·같은 스크립트).
- 데이터: 10만 건, 회원 50명(회원당 2,000건), view_date 2023-01-01~2025-12-31 균등 랜덤, 삽입 순서와 날짜 무관, 테이블 4,723 페이지(37MB). 측정 회원 7의 2025-06 = 65건(전체의 0.065%). 적재 후 `ANALYZE`.
- 각 쿼리를 `EXPLAIN (ANALYZE, BUFFERS)`로 3번 실행해 가장 빠른 회차를 기록(`run_stage()` 함수). 8개 쿼리: findActiveDays, countByCategory, countByGenre, getAverageRating, countByMonth, findMostActiveDay, findByYear, findByYearAndCategory.
- 인덱스는 요청서의 `(user_id, view_date)`에 해당하는 실제 인덱스 `(member_id, view_date)`를 썼다. 쿼리에는 현재 코드처럼 `member_id = 7`을 항상 넣었다.

### 결과 표 (로컬 Docker PG17, best of 3)
| 단계 | 인덱스 | 쿼리 형태 | Scan 방식 | Execution Time | 읽은 버퍼(shared hit, read는 전부 0) |
|---|---|---|---|---|---|
| 1 | 없음(PK만) | 옛 형태 (TO_CHAR/EXTRACT) | Seq Scan (대부분 Parallel Seq Scan) | 12.2 ~ 14.7 ms | 4,723 ~ 4,837 |
| 2 | (member_id, view_date) | 옛 형태 그대로 | Bitmap Index Scan + Bitmap Heap Scan | 2.0 ~ 4.8 ms | 2,008 (7개 쿼리 모두 동일) |
| 3 | (member_id, view_date) | 범위 조건 (현재 코드) | Bitmap Index Scan + Bitmap Heap Scan | 월 쿼리 6개 0.07 ~ 0.15 ms, 연 쿼리 2개 0.46 ~ 0.48 ms | 월 쿼리 68, 연 쿼리 643 |

쿼리별 실행 시간(ms) — 단계 1 / 2 / 3: findActiveDays 14.6/2.9/0.14, countByCategory 13.9/3.1/0.14, countByGenre 13.9/3.0/0.14, getAverageRating 13.0/3.5/0.08, countByMonth 13.2/4.0/0.07, findMostActiveDay 14.7/4.8/0.15, findByYear 14.6/2.6/0.48, findByYearAndCategory 12.2/2.0/0.46.

대표 계획 (countByMonth, 1회 실행한 EXPLAIN 텍스트):
- 단계 2: `Bitmap Index Scan ... Index Cond: (member_id = 7)` → `Bitmap Heap Scan ... Filter: (to_char(view_date, 'YYYY-MM') = '2025-06')`, `Rows Removed by Filter: 1935`, `Heap Blocks: exact=2000`, 4.1 ms
- 단계 3: `Index Cond: ((member_id = 7) AND (view_date >= '2025-06-01') AND (view_date < '2025-07-01'))`, `Heap Blocks: exact=65`, 0.23 ms

### Supabase 결과 (사용자 실행, PostgreSQL 17.6, 같은 스크립트·best of 3)
| 쿼리 | 1단계 Seq Scan (ms / 버퍼) | 2단계 옛 형태+인덱스 | 3단계 범위+인덱스 |
|---|---|---|---|
| findActiveDays | 16.5 / 4,723 | Index Only Scan, 0.67 / 9 | Index Only Scan, 0.062 / 4 |
| countByCategory | 17.8 / 4,723 | Bitmap Heap Scan, 3.66 / 2,008 | Index Scan, 0.091 / 68 |
| countByGenre | 17.8 / 4,723 | Bitmap Heap Scan, 3.50 / 2,008 | Index Scan, 0.093 / 68 |
| getAverageRating | 17.2 / 4,723 | Bitmap Heap Scan, 3.24 / 2,008 | Index Scan, 0.069 / 68 |
| countByMonth | 17.2 / 4,723 | Index Only Scan, 1.14 / 9 | Index Only Scan, 0.031 / 4 |
| findMostActiveDay | 17.4 / 4,726 | Index Only Scan, 1.16 / 9 | Index Only Scan, 0.072 / 4 |
| findByYear | 16.6 / 4,723 | Bitmap Heap Scan, 2.64 / 2,008 | Bitmap Heap Scan, 0.611 / 643 |
| findByYearAndCategory | 16.1 / 4,723 | Bitmap Heap Scan, 2.20 / 2,008 | Bitmap Heap Scan, 0.609 / 643 |

(모든 단계에서 `shared_read` = 0, 즉 디스크 읽기 없이 캐시 hit. 인덱스 이름은 전부 `idx_content_member_view_date`.)

로컬과 달라진 점과 해석:
- **결론은 로컬과 같다.** 1단계는 전부 Seq Scan(4,723 버퍼, 16~18 ms). 함수 조건(2단계)에서도 인덱스는 쓰이지만 `member_id` 접두사로만 쓰이고, 범위 조건(3단계)에서 `view_date`까지 인덱스 조건이 되어 읽는 양이 크게 줄었다. 2→3단계 속도 차: 집계 쿼리 약 40배(countByCategory 3.66→0.091 ms), countByMonth 약 37배(1.14→0.031 ms), 연 쿼리 약 4배(2.6→0.61 ms).
- **Index Only Scan이 나왔다**(로컬에는 없었음): findActiveDays·countByMonth·findMostActiveDay는 `member_id`·`view_date`만 필요해서 테이블(힙)을 읽지 않고 인덱스만 읽는다. 2단계에서도 버퍼가 9로 작은 이유다. 다만 2단계는 `view_date` 조건이 인덱스 조건이 아니라 해당 회원의 인덱스 항목 2,000개를 전부 읽으며 함수를 평가하는 방식이고(3단계는 65개만), 그래서 4→9 버퍼, 0.03~0.07 → 0.7~1.2 ms 차이가 난다.
- `category`/`genre`/`rating`이 필요한 쿼리(countByCategory·Genre·AverageRating)는 힙 접근이 필요해서 2단계 2,008 버퍼 → 3단계 68 버퍼가 가장 큰 차이다. 3단계에서는 플래너가 Bitmap 대신 일반 Index Scan을 택했다(65행 정도로 적을 때 선택됨).
- Index Only Scan이 가능했던 이유는 Supabase 테이블의 visibility map이 채워져 있었기 때문으로 **추정**한다(적재 직후 autovacuum이 돌았을 가능성). 로컬 컨테이너는 적재 직후라 비어 있어 Bitmap Heap Scan이 나왔다. 이 원인은 `pg_stat_user_tables`/`relallvisible`을 확인하지 않아 **미검증**이다.
- 이 데이터에서 Index Only Scan은 visibility map 상태에 의존하므로, 운영에서 쓰기가 계속 일어나는 테이블은 같은 결과를 보장하지 않는다.
- 한계는 로컬과 동일: `read=0`이라 디스크 I/O 비용 미반영, 실제 데이터는 10만 건보다 훨씬 적을 것(실제 건수는 `90-check-real-schema.sql` (4)). 유니크 제약만 있는 상태(40번)와 실제 스키마 점검(90번) 결과는 아래에 있다.

### 가설 대비 실제 (꾸미지 않고 기록)
- 가설 "2단계에서는 함수 때문에 인덱스가 사용되지 않고, 3단계에서만 Index/Bitmap Scan이 쓰인다" → **절반만 맞았다.**
  - 맞은 부분: 함수가 씌워진 `view_date` 조건은 **Index Cond에 들어가지 못하고** 힙에서 걸러내는 `Filter`로 처리된다(2,000행을 읽어 1,935행 버림). 범위 조건일 때만 `view_date`가 Index Cond에 들어가 65행만 읽는다.
  - **틀린 부분**: 2단계에서도 인덱스는 **쓰였다.** 인덱스의 선두 컬럼이 `member_id`이고 쿼리에 `member_id = 7`이 있어서, 그 부분만 인덱스를 탔기 때문이다(회원 1명이 전체의 2%). "함수 때문에 Seq Scan으로 돌아간다"는 설명은 이 인덱스 구성에서는 사실이 아니다.
- 1→2단계 개선(약 4배)의 대부분은 날짜가 아니라 **member_id 필터링** 덕분이다. 2→3단계(월 쿼리 약 20~60배 빠름·힙 페이지 2,000→65, 연 쿼리는 약 4~5배·2,000→638)가 "컬럼에 함수를 씌우지 않은 효과"이다.
- 보조 관찰 (참고용, best-of-3 표본 아님): 인덱스 없이 범위 쿼리만 쓰면 `Seq Scan`, 21.6 ms(1회 실행). 즉 범위 조건 자체는 인덱스가 있어야 의미가 있다.
- 참고 실행(`40-reference-real-schema.sql`): 실제 DB처럼 유니크 제약 (member_id, external_id, category)만 있고 view_date 인덱스는 없는 상태에서도 플래너는 그 유니크 인덱스를 member_id 접두사로 사용했다(옛 형태 2.6~4.1 ms / 버퍼 2,014, 범위 형태 1.8~2.2 ms / 2,014). 단계 1의 "인덱스 없음"은 실제 상태와 다르고, 실제 DB에서는 유니크 인덱스가 이미 member_id 필터를 도와준다. Supabase에서 실행한 40번 결과도 같다: 유니크 인덱스(`uk_content_member_external_category`)만 있을 때 전부 Bitmap Scan, 옛 형태 2.8~3.5 ms / 버퍼 2,014~2,017, 범위 형태 2.0~2.1 ms / 2,014. `view_date` 인덱스가 없으면 날짜 조건 유무와 상관없이 회원의 2,000행을 힙에서 읽는다(범위 형태가 약간 빠른 건 힙에서 필터링하는 비용 차이로 보이나 미검증). `findByYearAndCategory`만 0.45~0.51 ms / 339 버퍼로 낮은데, `category`가 유니크 인덱스의 세 번째 컬럼이라 인덱스 안에서 category를 먼저 걸러 힙 접근이 줄어든 것으로 **추정**한다(339 ≈ 2,000건의 1/6). 실행 계획 텍스트를 열어 확인하지는 않았다.

### 한계 (이 숫자로 주장할 수 없는 것)
- Supabase가 아닌 로컬 컨테이너. 모든 읽기가 shared buffers hit(`read=0`)이라 디스크 I/O 비용이 반영되지 않았다(실서버가 더 느릴 수 있고, 페이지 수 차이가 시간 차이로 더 크게 나타날 수 있다).
- 회원별 행이 힙 전체에 흩어진 랜덤 분포라 member_id 접두사 스캔에 불리한(힙 페이지를 많이 읽는) 편이다. 실제 사용자는 시간순으로 삽입되므로 페이지가 덜 흩어질 가능성이 있다 (미확인).
- 쿼리에 리터럴을 썼고, 앱은 바인드 파라미터(JDBC prepared statement)를 쓴다. 파라미터화 쿼리의 계획은 달라질 수 있다(미확인).
- **실제 데이터 규모는 10만 건이 아니다.** `90-check-real-schema.sql` (4) 결과 실제 `public.content`는 **1행**이다. 이 규모에서는 플래너가 어차피 Seq Scan을 택하므로 현재 운영 데이터로는 인덱스 효과가 측정되지 않는다. 위 수치는 "데이터가 늘었을 때"를 가정한 scratch 데이터 결과이고, 현재 사용자 체감 성능을 설명하는 값이 아니다.

## B. 통계 쿼리 N+1 / 불필요 조회 점검
**실행해서 확인하지 못했다. 아래는 모두 "코드상 예상"이다.** (앱을 띄우면 Supabase에 붙고, Testcontainers 테스트를 새로 만드는 것은 코드 추가라 범위 밖. `spring.jpa.show-sql=true`는 이미 켜져 있으므로 앱 실행 시 로그로 확인할 수 있다.)

- `StatisticsService.getMonthlyStatistics` 1회 호출 = **SELECT 6개**: countByCategoryInterface, countByGenreInterface, getAverageRating, countByMonth(이번 달), countByMonth(전월), findMostActiveDay. 전부 집계/프로젝션 쿼리이고 엔티티를 로딩하지 않는다. 한 `readOnly` 트랜잭션 안에서 같은 커넥션으로 순차 실행.
- 요청마다 추가로 회원 조회는 없다: JWT 필터가 claim으로 `AuthenticatedMember`를 만든다 (decisions 2026-10-24).
- **N+1 없음(코드상).** 반복 호출되는 쿼리는 countByMonth 2회뿐이고, 이는 N+1이 아니라 기간만 다른 고정 2회다. `Content.highlights`(LAZY OneToMany)·`member`(LAZY ManyToOne)는 통계 경로에서 엔티티를 로딩하지 않으므로 접근 자체가 없다.
- `ContentResponseDto(Content)` 생성자는 id/title/authorOrDirector/category/viewDate/rating/thumbnailUrl만 읽는다. `highlights`와 `member`를 건드리지 않으므로 `getFilteredContents`(목록 조회)에서 추가 쿼리는 코드상 나가지 않는다. 쿼리 1회(`findByYear` 등)로 끝난다. 다만 `Content`는 `comment`(TEXT) 등 전체 컬럼을 가져오는 엔티티 조회라 목록 용도로는 필요 이상의 컬럼을 읽는다(아래 제안).
- `open-in-view`는 설정하지 않아 Spring 기본값(true)으로 보인다(application.yml에서 해당 키 검색 결과 없음). 위 경로는 LAZY 접근이 없어 영향이 없다.
- **통합 가능한 쿼리 후보 (제안만, 수정 안 함):**
  1. countByCategory + countByMonth(이번 달) + getAverageRating → `GROUP BY category`로 `COUNT(*)`, `SUM(rating)`, `COUNT(rating)`를 한 번에 가져오고 자바에서 합산(평균은 SUM/COUNT로 가중 계산해야 평균의 평균 오류가 없음). 3개→1개.
  2. countByMonth 2회 → 범위 `[prevStart, end)` 한 번에 `COUNT(*) FILTER (WHERE view_date >= :start)`와 전체 `COUNT(*)`. 2개→1개.
  3. 위 둘을 적용하면 6개→3~4개. 효과는 왕복 횟수 감소(쿼리당 지연이 큰 원격 DB일수록 이득)이며 **현재 규모에서 실제 병목인지는 측정하지 않았다**(단계 3 기준 개별 쿼리는 0.1ms 수준).
  4. 목록 조회(`findByYear` 등)를 DTO 프로젝션으로 바꾸면 `comment` TEXT 전송을 줄일 수 있다.
- 일관성 관찰: 6개 쿼리는 한 `readOnly` 트랜잭션이지만 기본 격리(READ COMMITTED)라 쿼리마다 스냅샷이 다르다. 사이에 다른 요청이 저장하면 카테고리 합계와 이번 달 총수가 어긋날 수 있다. 통합 쿼리(위 1·2)는 이 문제도 줄인다. 개인 프로젝트 규모에서는 영향이 작다.

## C. 트랜잭션 경계 / 중복 체크 동시성 점검
코드 분석이며 **동시 실행 재현은 하지 않았다.** `50-concurrency-demo.sql`은 사용자가 Supabase에서 실행해 "success, no rows returned"만 확인됐는데, 이는 준비 단계(테이블 생성)뿐이며 세션 2개로 나눠 실행하는 단계는 수행되지 않았으므로 경쟁 상태 재현 결과는 없다.

### C-1. check-then-act 분석
`saveContent`는 `isAlreadySaved`(SELECT EXISTS) → `save`(INSERT) 순서다. READ COMMITTED에서 같은 (member_id, external_id, category) 요청 A, B가 동시에 오면 둘 다 EXISTS=false를 보고 둘 다 INSERT로 진행할 수 있다. **서비스 코드만으로는 두 번째 요청을 막지 못한다.** 막는 것은 DB의 유니크 제약이다.
- 제약이 있으면: B의 INSERT는 A 커밋을 기다렸다가 SQLSTATE `23505`로 실패 → `DataIntegrityViolationException` → `isUniqueViolation`이 원인 체인에서 SQLState를 찾아 `IllegalStateException("이미 저장된 콘텐츠입니다.")`로 바꿈 → `GlobalExceptionHandler`가 400 → **순차 중복(EXISTS 체크로 던진 경우)과 응답이 같다.** 예외가 호출자까지 전파되므로 트랜잭션은 롤백되고 `UnexpectedRollbackException`은 나지 않는다(코드상).
- 제약이 없으면: 두 행이 모두 저장된다(통계/캘린더에 중복 반영).
- FK 위반(23503, 토큰은 유효한데 회원이 삭제된 경우)은 중복이 아니므로 그대로 던져져 `handleAllExceptions`에서 **500**이 된다.

### C-2. 실제 DB 제약 확인
- 엔티티 선언: `@Table(uniqueConstraints = uk_content_member_external_category (member_id, external_id, category), indexes = idx_content_member_view_date (member_id, view_date))` — 확인함.
- 실제 DB(Supabase `public.content`): **확인했다(사용자 실행 결과).**
  - 인덱스: `content_pkey`, `idx_content_member_view_date (member_id, view_date)`, `uk_content_member_external_category UNIQUE (member_id, external_id, category)` 모두 존재.
  - 제약: PK, FK `member_id → members(id)`, UNIQUE `uk_content_member_external_category`, CHECK `content_category_check`(BOOK/MOVIE/TV/ANIME/ANIME_MOVIE/ANIME_TVA/ALL), CHECK `content_status_check`.
  - 중복 행: 없음(조회 결과 0행). 행 수: 1.
  - 따라서 C-1의 "제약이 있으면" 분기가 실제 DB에서 성립한다. `ddl-auto: update`로 제약이 생성되지 않았을 가능성은 사라졌다.
  - CHECK 제약은 NULL을 통과시키므로 category가 NULL인 행은 여전히 가능한지는 NOT NULL 여부를 따로 확인하지 않아 **미확인**이다.
- `external_id`가 NULL인 직접 입력은 PostgreSQL 유니크가 NULL을 서로 다른 값으로 보므로 제약에 걸리지 않는다(decisions 2026-10-27에 이미 기록).

### C-3. 선택지 비교
| 선택지 | 장점 | 단점 / 트레이드오프 |
|---|---|---|
| (1) DB 유니크 제약 + 위반 예외를 "이미 저장된 콘텐츠"로 변환 **(현재 코드가 이 방식)** | 동시성에서 정합성을 DB가 보장. 락 불필요, 성능 영향 거의 없음. 응답이 순차 중복과 같은 400이라 일관됨 | 제약이 실제 DB에 있어야 성립(C-2). `isUniqueViolation`이 SQLState에 의존하고 `GlobalExceptionHandler`는 `IllegalStateException`이면 무엇이든 400으로 묶으므로 "중복"이라는 의미 구분이 메시지 문자열뿐. 409가 더 정확하지만 기존 400 흐름 유지(로그인 중복 아이디만 409) |
| (2) 비관적 락 / SERIALIZABLE | 이론상 check-then-act 자체를 직렬화 | 존재하지 않는 행에는 `SELECT ... FOR UPDATE`로 잠글 대상이 없음(→ 회원 행 락 등 우회 필요). SERIALIZABLE은 직렬화 실패(40001) 재시도 로직이 필요. 복잡도·지연 증가, 유니크 제약으로 이미 해결되는 문제에 과함 |
| (3) 현재 유지(체크만, 제약 없이) | 구현 없음 | 제약이 없다면 동시 요청에서 중복 저장. 지금 코드는 제약이 있으므로 사실상 (1)과 같다 |

### C-4. 권장안
(1) **유지.** 코드 변경은 불필요하다. 단, ① 실제 DB에 제약이 있는지 `90-check-real-schema.sql`로 확인하는 것이 선행 조건이고, ② 중복 행이 이미 있어 제약이 안 생겼을 가능성에 대비해 (3) 쿼리를 본다. ③ `isAlreadySaved` 선검사는 친절한 메시지와 불필요한 INSERT 시도 회피용 "빠른 경로"로 유지하고 최종 방어선은 제약이라는 역할 구분을 decisions에 남긴다(회원 이메일 중복과 같은 구조, decisions 2026-11-02).

### C-5. @Transactional 구성 점검
- `ContentService`: 클래스 `@Transactional(readOnly = true)` + `saveContent`만 `@Transactional`(쓰기)로 오버라이드 — 적절하다. `isAlreadySaved`, `findSavedKeys`는 읽기 전용 상속. `getFilteredContents`의 메서드 수준 `@Transactional(readOnly = true)`는 클래스 설정과 중복이라 불필요하지만 해가 없다(정리는 리팩토링이라 하지 않음).
- `StatisticsService.getMonthlyStatistics`, `CalendarService.getMonthlyActivity`: 읽기만 하므로 `readOnly = true`가 적절. 여러 쿼리를 한 커넥션/트랜잭션에 묶고 Hibernate flush·dirty checking을 생략하는 이점이 있다. 다만 격리 수준은 올려주지 않는다(위 B의 스냅샷 관찰).
- `saveContent` 안의 `getReferenceById`는 SELECT 없이 프록시를 만들고, 없는 회원이면 INSERT에서 FK 위반이 난다(위 C-1의 500).
- `isAlreadySaved`가 컨트롤러 `/check`에서 단독 호출될 때도 클래스 레벨 readOnly 트랜잭션이 적용된다.

## 정리 (면접/트러블슈팅용)
1. **문제 상황**: 월별 통계·캘린더 쿼리가 인덱스를 타는지 한 번도 확인하지 않았다. 컬럼에 함수를 씌우면 인덱스를 못 탄다고 알고만 있었다. 저장 API는 check-then-act 구조라 동시 요청에서 중복이 들어갈 수 있는지도 점검 대상이었다.
2. **고려한 선택지**: 측정 환경 ① 실DB(오염·행 수 부족으로 Seq Scan) ② Supabase에 scratch 스키마+10만 건 ③ 로컬 컨테이너. 동시성 ① 유니크 제약+예외 변환 ② 비관적 락/SERIALIZABLE ③ 현상 유지.
3. **선택 이유**: 측정은 scratch 스키마 SQL을 만들고 로컬 일회용 PG17에서 먼저 검증·측정(운영 DB 오염 0, 스크립트 재현 가능). 한계는 로컬이라 절대 시간과 디스크 I/O를 대표하지 못한다는 것. 동시성은 DB 유니크 제약이 최종 방어선인 현재 구조(①) 유지 권장: 락 없이 정합성 보장, 비용은 제약이 실제 DB에 있어야 한다는 전제와 SQLState 의존.
4. **막혔던 부분과 해결**: 가설("함수 때문에 인덱스를 아예 못 탄다")이 틀렸다. 2단계에서도 인덱스는 쓰였는데 선두 컬럼 `member_id`만 Index Cond였고 `view_date`는 Filter였다. EXPLAIN 텍스트의 `Index Cond`와 `Filter` 줄을 비교해서 알았다. 또 bash heredoc으로 SQL을 쓰다 파일이 중간에서 잘려 Write 도구로 다시 만들었다.
