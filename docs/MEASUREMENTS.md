# 측정 A: 로컬 PC(Upstash 도쿄)

측정 A와 측정 B는 환경과 측정 대상이 달라 서로 비교하지 않음. 요약은 [DESIGN.md](DESIGN.md) 1-1 참고.

## 배경과 결정 과정 (트러블슈팅 기록: 검색 API Redis 캐싱)

**1. 문제 상황**

통합 검색 API가 매 요청마다 외부 API를 호출해서, 같은 검색어도 항상 외부 API 지연을 겪음. 특히 TMDB는 응답이 느림.

**2. 고려한 선택지**

- A. `SearchService.search()` 진입점에 `@Cacheable` (전체 카테고리 캐싱)
- B. `TmdbSearchService` 등 provider 단위로 선택 적용
- C. Redis 위치: 로컬 Docker vs 클라우드(Upstash 도쿄)

**3. 선택 이유**

- 처음엔 A안으로 구현함(어노테이션 한 줄, 요청 단위와 캐시 단위 일치).
- 캐싱 있음/없음/히트를 직접 측정한 결과, **TMDB는 234ms → 43ms(약 82% 단축)**, **Kakao는 27ms → 45ms로 오히려 느려짐**. 원인은 Kakao 원본이 이미 빨라서 원격 Redis 왕복(약 40ms)이 더 컸기 때문.
- 따라서 B안(TMDB에만 적용)이 측정상 더 합리적임. 캐싱의 이득이 응답 속도뿐이 아니라 **외부 API 호출 횟수 절감**(호출 한도 방어)에도 있어서, Kakao 캐싱을 유지할지는 속도와 호출 절감을 따로 판단해야 함.
- 한계: 검색어 5건씩, 로컬 PC 측정. 절대 수치보다 경향으로 해석.

**4. 막혔던 부분**

- Docker Desktop WSL2 오류 → Upstash로 우회
- 에디터 자동 생성 클래스 위에 코드를 이어 붙여 `package` 중복 → 파일 전체 교체
- Upstash `host`에 `https://` 주소를 넣을 뻔함 → 도메인만 사용
- Upstash 무료 DB가 14일 미사용으로 자동 삭제 → 캐시는 재생성 가능해서 새 DB 생성. Redis 접속 실패가 검색 API 500으로 번지는 약점도 확인 → 이후 `CacheErrorHandler`로 캐시 장애 시 외부 API로 대체 호출하도록 보완
- 처음엔 "미스 vs 히트" 비교로 67% 단축이라 결론냈다가, `@Cacheable`을 뺀 기준선을 재서 **미스가 캐싱 없음과 다르다는 점**을 발견하고 결론을 정정함

### 측정 조건 (나중에 다시 볼 때 필요한 정보)

- 환경: 로컬 PC(서울), Redis는 Upstash 무료 DB(도쿄 리전), 검색어당 1회 측정
- 캐싱 없음: `SearchService`의 `@Cacheable`을 뺀 상태에서 워밍업 1회 후 측정
- 캐시 미스: `@Cacheable`을 다시 붙인 뒤 처음 호출한 값(Redis 조회, 외부 호출, 저장이 모두 포함)
- 캐시 히트: 미스 직후 같은 검색어를 다시 호출한 값(TTL 10분 이내)
- Kakao의 미스/히트는 앱을 막 켠 직후에 측정했고, 캐싱 없음 값은 재시작 후 워밍업을 거쳐 측정함. 그래서 Kakao 미스(특히 데미안 229ms)에는 초기화 비용이 섞였을 수 있음.
- 이 값은 표본이 5건이라 절대 수치보다 경향으로 해석함.
