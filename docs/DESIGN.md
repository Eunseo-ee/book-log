# 설계 결정과 측정

README의 하이라이트 3개에서 다루지 못한 설계 결정과, 측정의 조건·한계를 정리했습니다.
수치는 모두 직접 측정한 값이며, 측정 환경이 다른 값은 섞어 쓰지 않았습니다.

## 1. 측정

### 1-1. Redis 캐싱 (TMDB만 적용)

두 가지 측정이 있고, 환경과 대상이 다르므로 서로 비교하지 않습니다.

**(A) 로컬 PC → Upstash 도쿄, 검색 API 단독 호출**

| 대상 | 캐시 없음 | 캐시 히트 | 결과 |
| --- | --- | --- | --- |
| TMDB 검색 | 234.4ms | 43.2ms | 약 82% 단축 → 적용 |
| Kakao 검색 | 26.6ms | 44.6ms | 오히려 느려짐 → 적용 안 함 |

- 조건: 검색어 5건, 각 1회.
- 한계: 표본이 작아 절대 수치보다 경향으로 해석합니다.
- 같은 측정에서 TMDB 캐시 미스는 Redis 조회·저장 때문에 캐싱 없음보다 약 52ms 더 걸렸습니다(미스 평균 286.8ms − 캐싱 없음 234.4ms, 검색어별 값은 [MEASUREMENTS.md](MEASUREMENTS.md)의 측정 A). 히트율이 낮으면 캐시가 오히려 손해일 수 있어, 적용 범위를 측정으로 정한 근거가 됐습니다.
- Kakao는 원본이 이미 빨라서(26.6ms) 원격 Redis 왕복 시간이 더 커졌습니다.

**(B) 배포 환경(Cloud Run), 서버 측 `httpRequest.latency` 기준**

- 조건: 검색어 5개를 각각 연속 2회 실행해 첫 검색(미스)과 두 번째 검색(히트)을 비교. 카테고리 ALL, 1페이지, 인스턴스 1개, 워밍업 검색 제외.
- 결과: 미스 중앙값 342ms → 히트 중앙값 88ms (약 74% 단축).
- 한계: 표본이 작아 절대 수치보다 경향으로 해석합니다.
- (A)보다 단축률이 낮은 이유: (B)는 카테고리 ALL이라 캐시하지 않는 Kakao 요청을 포함한 전체 응답 시간입니다. (A)는 TMDB 단독 측정입니다.

### 1-2. 월별 조회 인덱스

**조건:** 로컬 PostgreSQL 17(Docker), 회원 50명 × 2,000건 = 10만 건. 월 조회 대상은 한 회원의 2025-06(65건). 각 쿼리를 `EXPLAIN (ANALYZE, BUFFERS)`로 3회 실행해 가장 빠른 회차를 기록.

| 단계 | 인덱스 | 쿼리 형태 | 스캔 방식 | 실행 시간 | 읽은 버퍼 |
| --- | --- | --- | --- | --- | --- |
| 1 | 없음 | `TO_CHAR(view_date,'YYYY-MM')` | Seq Scan | 8.5~10.4ms | 약 4,700~4,800 |
| 2 | `(member_id, view_date)` | 위와 동일 | Bitmap Index Scan | 1.2~1.7ms | 2,008 |
| 3 | `(member_id, view_date)` | 날짜 범위 조건(현재 코드) | Bitmap Index Scan | 월 쿼리 0.07~0.12ms | 68 |

- 1→2단계 개선은 대부분 선두 컬럼 `member_id` 덕분이었습니다. 2단계에서도 `Index Cond`는 `member_id`뿐이고, 날짜는 `Filter`로 처리되어 그 회원의 2,000행을 읽고 1,935행을 버렸습니다.
- 2→3단계에서 컬럼에 함수를 씌우지 않고 범위 조건으로 바꾸자 `view_date`까지 `Index Cond`에 들어가 힙 접근이 2,000페이지에서 65페이지로 줄었습니다.
- 처음에는 "함수를 쓰면 인덱스를 못 탄다"고 생각했지만 이 인덱스 구성에서는 사실이 아니었습니다. 가정하지 않고 측정해야 한다는 점을 배웠습니다.
- 한계: 로컬 Docker 수치라 절대 시간은 서버와 다릅니다. 모든 읽기가 캐시 hit라 디스크 I/O는 반영되지 않았고, 데이터는 행이 힙 전체에 랜덤하게 흩어진 분포입니다. 운영 DB의 현재 데이터는 1행이라 이 수치는 "10만 건이 되었을 때"를 가정한 값입니다.

## 2. 설계 결정과 트레이드오프

### 외부 API와 캐시

- **검색 캐시는 TMDB에만, TTL 10분.** 캐시 키는 `query:category:page`이고, 빈 결과는 캐시하지 않습니다(`unless`). 외부 장애 시 빈 응답이 반환되는데, 캐시하면 TTL 동안 장애 결과가 고정되기 때문입니다. 우리 서비스가 수정하지 않는 외부 데이터라 무효화는 TTL 만료에 맡기고 `@CacheEvict`는 쓰지 않습니다.
- **`isSaved`는 캐시 바깥에서 매 요청마다 채움.** 사용자별 상태라 캐시에 넣으면 10분간 낡은 값이 나갑니다. 대신 요청마다 IN 쿼리 한 번이 듭니다.
- **Redis는 fail-open.** 캐시 오류는 삼키고 외부 API를 직접 호출합니다. `spring.data.redis.timeout`과 `connect-timeout`은 1s로 두었습니다. Redis가 응답하지 않으면 요청당 최대 약 2초(GET + PUT)까지 지연될 수 있고, 정상 상태의 캐시 히트는 35~88ms라 1s는 충분한 여유입니다. 더 줄이면 일시적인 지연에도 캐시가 불필요하게 실패할 수 있어 1s를 유지했습니다.
- **외부 API 장애는 provider 단위로 격리.** Kakao·TMDB 중 하나가 죽어도 나머지 결과를 반환하고, 전부 실패해도 200 + 빈 결과입니다. 한계: 프론트가 "결과 없음"과 "장애"를 구분하지 못합니다.
- **캐시 오류 로그는 마스킹.** 캐시 이름, 동작, 키의 SHA-256 앞 8자, 예외 클래스, 루트 원인 한 줄만 남기고 스택트레이스와 검색어 원문은 남기지 않습니다. 트레이드오프: 해시로는 어떤 검색어인지 알 수 없습니다.

### 인증·인가

- **JWT는 access/refresh를 같은 키로 서명하고 type claim으로 구분.** 필터는 access만, refresh 엔드포인트는 refresh만 인정합니다.
- **필터는 요청마다 DB를 조회하지 않고 토큰 claim으로 인증.** STATELESS와 DB 부하 감소가 이유입니다. 트레이드오프: 회원이 삭제되거나 role이 바뀌어도 access 토큰이 만료될 때까지는 이전 정보로 인증됩니다. 그래서 access 만료는 짧게 두고, refresh 때만 회원 존재를 DB로 확인합니다.
- **로그인 실패는 아이디 없음과 비밀번호 틀림을 구분하지 않음.** 같은 예외, 같은 401, 같은 메시지입니다. 없는 아이디도 더미 해시와 BCrypt 비교를 한 번 해서 응답 시간으로도 구분되지 않게 했습니다.
- **비밀번호는 문자 수(8~64)에 더해 UTF-8 72바이트 이하.** BCrypt가 72바이트 초과분을 예외 없이 잘라 해시하므로, 한글 비밀번호의 뒷부분이 조용히 무시되는 것을 입력 단계에서 막았습니다.
- **토큰 저장 위치.** access 토큰은 메모리에만 두고(새로고침 시 refresh로 복구), refresh 토큰만 `localStorage`에 저장합니다. 백엔드가 refresh를 응답 body로만 주고 쿠키를 설정하지 않아, httpOnly 쿠키는 백엔드·CORS 수정 없이는 불가능했습니다.

  | 선택지 | 평가 |
  | --- | --- |
  | ① refresh만 localStorage (선택) | XSS 한 번에 7일짜리 refresh가 탈취될 수 있지만, CSRF에는 안전하고 CORS `allowCredentials`가 필요 없음 |
  | ② httpOnly 쿠키 | XSS로 토큰은 못 훔치지만 SameSite/CSRF 대응과 백엔드·CORS 수정이 필요 |
  | ③ access도 localStorage | 구현은 가장 단순하지만 노출 면적이 가장 넓음 |

  한계: 서버가 refresh 토큰을 저장하지 않아 탈취돼도 폐기할 수 없습니다. httpOnly 쿠키 전환과 서버 측 폐기는 향후 개선안입니다.
- **하이라이트 소유권 검사는 서비스에서.** 남의 하이라이트는 403, 없는 id는 404로 구분해 응답합니다. 트레이드오프: 403이 "존재하지만 권한 없음"을 알려 id 열거가 가능합니다.

### 데이터 모델

- **`Member.id`는 Long.** 기존 `Content.userId`와 타입이 맞고 id가 URL·응답에 노출되지 않아 열거 위험이 낮습니다. 외부에 id를 노출해야 하면 UUID나 공개 식별자를 쓸 계획입니다.
- **`Content` ↔ `Member`는 `@ManyToOne(LAZY)`.** DB FK로 참조 무결성을 보장합니다. 대신 엔티티 결합과 저장 시 `getReferenceById`가 필요합니다.
- **유니크 제약 `(member_id, external_id, category)`.** 사용자별 중복 저장을 DB가 막습니다. 동시 요청으로 유니크 위반이 나면 서비스가 SQLState(23505)로 구분해 기존 중복 흐름(400)으로 바꿉니다. 락이나 SERIALIZABLE은 채택하지 않았습니다.
- **월·연도 조건은 `[시작일, 다음 기간 시작일)` 범위로.** 측정 결과는 1-2 참고.
- **선택 조건 조회는 Specification.** 조건이 null이면 null을 반환해 `and()`가 무시하게 합니다(JPQL의 `:p IS NULL OR ...`은 PostgreSQL에서 null 파라미터 타입 추론 오류 위험). 소유자 조건 `ownedBy(null)`은 "조건 없음"이 아니라 예외로 처리해, null이 전체 회원 노출로 이어지지 않게 했습니다.

### 운영·배포

- **설정은 환경변수로 주입.** 운영 이미지에는 yml이 들어가지 않습니다. 필수 값(API 키, JWT)이 비면 기동 시 실패합니다.
- **Dockerfile 기본 프로파일은 `prod`.** prod를 빠뜨리면 Swagger가 열리는 문제를 체크리스트가 아니라 이미지 기본값으로 막았습니다. 트레이드오프: 로컬 `docker run`에도 `APP_CORS_ALLOWED_ORIGINS`가 필요합니다.
- **CORS는 명시 origin만.** `*`는 기동 실패이고, prod에서 값이 없어도 기동 실패입니다. `allowCredentials`는 켜지 않았습니다(쿠키를 쓰지 않으므로).
- **헬스체크 분리.** liveness는 프로세스 상태만, readiness는 DB만 봅니다. Redis는 캐시라 어느 쪽에도 넣지 않았습니다.
- **시크릿은 Secret Manager 참조로 주입.** Cloud Run 환경변수는 콘솔에 평문으로 보이기 때문입니다.
- **Cloud Run minScale=0.** 비용 우선이라 콜드 스타트가 있어, 라이브 데모 대신 영상을 기본으로 둡니다.
- **시간 처리는 `Clock` 빈(Asia/Seoul) 주입.** 미래 날짜 검증과 통계 기본 연·월이 같은 시계를 쓰고, 테스트에서 KST 경계를 고정할 수 있습니다.

## 3. 개발 방식

전체를 Phase/task 단위로 나눠 진행했고, 각 task에 완료 기준과 트레이드오프를 문서화했습니다. 구현은 AI 코딩 도구와 함께 진행했으며, 요구사항 정의·설계 결정·테스트와 측정을 통한 검증은 직접 했습니다.
