# 트러블슈팅

README에 싣지 못한 문제 해결 기록입니다. 각 항목은 문제 → 시도 → 선택 → 알게 된 점 순서입니다.
측정 수치와 설계 배경은 [DESIGN.md](DESIGN.md)에 있습니다. 캐시가 조용히 죽어 있던 사례(④)는 README에도 요약했습니다.

## ① Redis: 느려지거나 죽어도 서비스는 살아야 한다

- **문제:** 캐시 장애가 곧 검색 장애로 번질 수 있고, 응답 없이 멈추는 경우도 있었습니다.
- **시도:** `CacheErrorHandler`로 캐시 오류 시 외부 API를 직접 호출하게 했습니다. command/connect timeout을 1s로 명시했고, 연결 거부뿐 아니라 무응답 멈춤까지 테스트했습니다. 빈 결과는 캐싱하지 않도록 `unless`를 걸었습니다.
- **선택:** timeout을 늘리면 Redis가 응답하지 않을 때 요청이 그만큼 더 오래 붙잡힙니다. 현재 설정(command·connect 각 1s)에서도 Redis 무응답 시 요청당 최대 약 2초(캐시 조회 GET + 저장 PUT, 빈 결과는 GET만)까지 지연될 수 있음을 코드 기준으로 계산했습니다. 정상 상태의 캐시 히트는 35~88ms라 1s는 충분한 여유이고, 더 줄이면 일시적인 지연에도 캐시가 불필요하게 실패할 수 있어 1s를 유지했습니다.
- **알게 된 점:** 캐시는 최적화일 뿐 의존성이 되면 안 됩니다. 장애 시 최악의 지연을 숫자로 계산해 두어야 합니다. (캐시가 조용히 죽어 있던 실제 사례는 ④)

## ② 로컬 Docker(WSL2) 오류 → Upstash로 대체

- **문제:** 로컬에서 Docker로 Redis를 띄우려 했으나 Docker 엔진 연결 오류로 컨테이너가 실행되지 않았습니다. WSL2 미설치가 원인으로 추정했습니다.
- **시도:** Docker Desktop 재실행과 `wsl --update`를 시도했으나 해결되지 않았습니다. WSL2를 처음부터 설치하고 가상화 설정까지 확인하는 경로는 소요 시간을 예측할 수 없고 이번 목표(캐싱 구현)와 거리가 멀어 포기했습니다.
- **선택:** 관리형 Redis(Upstash 도쿄)로 대체했습니다. 배포에서도 관리형 Redis를 쓸 가능성이 높아 개발 단계부터 같은 방식으로 맞췄습니다.
- **트레이드오프:** 무료 플랜은 14일 미사용 시 자동 삭제됩니다(실제로 DB가 삭제되어 새로 생성). 그래서 데모는 상시 운영하지 않고 영상으로 대체하기로 했습니다. 원격 Redis라 히트에도 왕복 시간이 들어 원본이 빠른 Kakao는 오히려 느려졌습니다(DESIGN.md 1-1). 접속 실패가 검색 장애로 번지는 약점은 ①에서 보완했습니다.
- **알게 된 점:** 인프라 선택은 설치 편의뿐 아니라 지연 시간 같은 성능 특성까지 따져야 합니다. 캐싱 적용 전에 캐싱 없음/미스/히트를 직접 측정해야 했습니다.

## ③ 시크릿 관리

- **문제:** 머지 중 파일에 옛 시크릿이 남아 있었고, 이 파일이 커밋에 함께 올라간 적이 있습니다.
- **조치:** 해당 파일을 삭제하고, 커밋에 포함됐던 값은 모두 변경(폐기·재발급)했습니다. JWT 시크릿은 재생성해 별도 yml에서만 관리하고 옛 값은 재사용하지 않습니다. 배포는 환경변수로 주입합니다.
- **알게 된 점:** 시크릿은 코드와 로컬 산출물에서 분리해야 하고, 노출 가능성이 있는 값은 삭제가 아니라 폐기와 재발급이 원칙입니다.

## ④ 운영에서 캐시가 한 번도 동작하지 않았는데, 서비스는 정상이었다

- **문제:** 배포 후 TMDB 검색은 정상 응답했지만 Upstash에 키가 없었고, 대시보드의 Commands가 0이었습니다. 캐시 오류를 삼키는 fail-open 설계 때문에 장애가 드러나지 않았습니다.
- **원인을 좁힌 과정:** 코드(`@Cacheable` 위치, self-invocation 여부) → 환경변수(host, port, SSL, 비밀번호 시크릿 존재) → 시크릿 값(끝 줄바꿈 여부) → 로그(요청마다 get/put 실패 WARN은 있으나 원인은 보이지 않음) 순으로 가설을 하나씩 제외했습니다.
- **선택지 비교:** (a) 추측으로 설정을 바꿔 보기 (b) 에러 핸들러에 스택트레이스를 켜서 운영에서 직접 증거 확인 (c) 로컬에서 redis-cli로 접속 테스트. 변경이 한 줄이고 실패하는 환경에서 근본 원인이 바로 나오는 (b)를 선택했습니다. 대가로 재배포가 필요하고 Redis가 죽어 있으면 로그가 쌓이므로 임시 진단으로만 사용했습니다.
- **원인:** 예외 체인에서 `WRONGPASS`(서버가 인증을 거절)를 확인했습니다. Secret Manager의 비밀번호가 Upstash의 현재 값과 달랐습니다. (이전 값이 왜 달랐는지는 확정하지 못했습니다.)
- **해결과 검증:** 시크릿을 줄바꿈 없이 재등록하고 새 리비전을 배포했습니다. Upstash에 키 6개가 생기고 TTL이 줄어드는 것을 확인했으며, 같은 검색어 반복 측정에서 중앙값 342ms → 88ms(약 74% 단축, 배포 환경 측정)였습니다.
- **이후 조치:** 임시 진단용 스택트레이스 로깅은 마스킹 핸들러로 교체했습니다. 지금은 캐시 이름, 동작, 키 해시 앞 8자, 루트 원인 한 줄만 남고 스택트레이스와 검색어 원문은 남지 않습니다.
- **알게 된 점:** 캐시 오류를 삼키는 설계는 서비스를 지키지만 장애를 숨깁니다. WARN 한 줄은 ERROR 필터에 걸리지 않아 스모크 테스트의 "ERROR 로그 없음"이 안전을 뜻하지 않았습니다. 캐시는 키 생성, TTL, 응답 시간으로 실제 동작을 확인해야 합니다.

## ⑤ Refresh 토큰으로도 접근이 되는 문제

- **문제:** 필터가 토큰 종류를 구분하지 않아 refresh 토큰이 인증으로 통과했습니다. refresh 토큰은 수명이 길어, 탈취되면 일반 API 접근에도 쓰일 수 있었습니다.
- **해결:** 토큰에 종류(access/refresh) claim을 넣고 필터는 access만 인정하게 했습니다. 만료·위조·refresh 접근 테스트를 추가했습니다.

## ⑥ 테스트가 조용히 skip되는 문제

- **문제:** Docker 연결 실패 시 Testcontainers 테스트 9개가 skip되었는데 빌드는 성공으로 표시됐습니다.
- **시도/해결:** CI 로그에서 skip 여부를 확인했고, Testcontainers 버전 업그레이드로 근본 해결했습니다. 테스트 이미지와 Supabase 실제 버전(PostgreSQL 17)이 일치하는지도 확인했습니다. 추가로, 이 테스트가 skip되거나 결과가 없으면 CI가 실패하도록 가드를 넣었습니다.
- **알게 된 점:** 초록불이 "검증됨"을 뜻하지 않습니다.

## ⑦ 헬스체크에 Redis가 섞이는 문제

- Cloud Run probe를 liveness / readiness로 분리해, 캐시 장애로 인스턴스가 재시작되지 않도록 했습니다. `/actuator/health`는 Redis를 포함하므로 probe에 쓰지 않았습니다.
- **알게 된 점:** 캐시처럼 없어도 동작하는 의존성의 장애가 인스턴스 재시작으로 이어지면 안 됩니다.

## ⑧ 입력 오류가 500으로 나가던 문제

- **문제:** 잘못된 파라미터, 범위 밖 값, 깨진 JSON이 400이 아니라 500으로 응답했습니다. 클라이언트 오류가 서버 오류로 보였습니다.
- **원인:** `GlobalExceptionHandler`에 해당 예외(`ConstraintViolationException`, `MethodArgumentTypeMismatchException`, `MissingServletRequestParameterException`, `HttpMessageNotReadableException`) 핸들러가 없어 최후의 `Exception` 핸들러가 받았습니다.
- **시도·비교:** `@Validated`를 빼고 서비스에서 검증하는 방법과 비교했고, 변경이 작은 핸들러 추가를 선택했습니다. `IllegalArgumentException` 전체를 400으로 매핑하는 방식은 코드 버그를 숨길 수 있어 피하고, 없는 리소스는 전용 예외(404)로 분리했습니다.
- **결과:** 8개 케이스를 수정 전후로 측정해 7개가 바뀌었고, 9개 테스트로 고정했습니다(500 → 400 5건, 없는 contentId 400 → 404, 하이라이트 저장 200 → 201). 나머지 1개는 400 그대로이고, 수정 전 측정 없이 추가한 1개가 9번째 테스트입니다. 오류 메시지에는 입력값을 되돌려 주지 않습니다.
- **알게 된 점:** 수정 중 길이 검증을 검사한다고 믿었던 테스트가 사실은 다른 예외에 우연히 맞아 통과하고 있었습니다. 통과하는 테스트도 무엇을 검증하는지 확인해야 합니다.
